Targets (spec §9): active RAM ≤ 150 MB; throughput ≥ cobalt (target 2–5x large files).

## Verdict

**NO-GO on the spec §9 RAM hard gate as measured.** The pipeline works end-to-end, but the active-job RAM target is missed by a wide margin, so M0 cannot certify the resource budget. Per spec §9 line 215 ("If targets miss, we adjust before building UI"), the mitigation levers below must be evaluated and re-measured before M1 UI work is gated in. This is a feasibility gate, not a performance certification.

- **RAM (hard gate, spec §9 line 40 / lines 208–209: active-job RAM ≤ 150 MB worst case, INCLUDING the yt-dlp + ffmpeg transients): MISSED.** `peak_RAM_MB` now measures the **total working set of the entire descendant process tree rooted at the bench PID** (bench + yt-dlp + its children + ffmpeg), which is the metric §9 actually gates on. Real measured YouTube peak: **400.7 MB** — **2.7x over** the 150 MB limit. The prior report's 20.0 MB was the bench process alone (the "Rust HTTP + buffers" component) and was an overclaim against this gate; it is superseded, not confirmed.
  - **Where the memory goes (independently corroborated):** the peak occurs in the **extract** state, and the dominant contributor is *not* Siphon's Rust code. Process-tree composition at peak: `siphon-bench.exe` 13.0 MB + `yt-dlp.exe` (PyInstaller bootloader) 8.8 MB + `yt-dlp.exe` (Python runtime) 97.4 MB + **`deno.exe` 288.5 MB** = 407.8 MB. Deno is yt-dlp's JavaScript interpreter, spawned for YouTube signature/nsig deciphering. It is a **great-grandchild** of the bench process (bench → yt-dlp bootloader → yt-dlp Python → deno), which is exactly why a transitive tree closure — not a direct-children sum — is required. The spec's "+ transient Python proc" budget did not anticipate this interpreter subprocess.
  - The **≤ 120 MB "Active, yt-dlp fallback"** row (line 208) is likewise **MISSED**, for the same reason. With the Deno grandchild excluded, the extract state measured ~104 MB — i.e. the Python runtime alone would have fit that row.
  - **Download-only state** (yt-dlp exited, merge not yet started): bench alone ~20 MB, consistent with the ≤ 80 MB "native extractor, no merge" row — but the native path was never successfully exercised (Reddit errored), so that row is **not certified**.
  - **Sequential-state nuance:** the states do not overlap — yt-dlp and Deno exit before the download finishes and ffmpeg starts. The tree peak therefore equals the worst *single* state (extract), not a simultaneous sum of all three. The ffmpeg merge transient is sub-second on this ~19 s clip and was **not separately resolved** by the sampling cadence (it never appeared as the peak); no merge-state figure is claimed.
  - **Verification that the number is real, not an artifact:** three real benchmark runs gave **383.4 / 375.2 / 400.7 MB** peak (run-to-run variance in Deno's working set). An independent WMI (`Win32_Process`) process-tree probe run around the benchmark — a different API, using explicit parent-PID links — measured **358.1 MB** and **407.8 MB** peaks with the same four-process composition, agreeing with sysinfo to within ~5% (the probe polled coarser than the 100 ms sampler). `peak_CPU%` is now also a **tree-wide sum** (325.0% here), so it can exceed 100% on a multi-core machine; it is not a single-process percentage.
- **Mitigation required before UI (spec line 215; levers per lines 117–118).** Candidates only — none has been measured, so none is claimed as a fix:
  1. **Native extractors shadowing yt-dlp** (lines 117–118) eliminate the Python + Deno processes entirely; the Rust-only download state measured ~20 MB. For YouTube specifically, lines 124–126 already flag a native extractor as the hardest item and an explicit risk — this measurement turns that risk into a blocking budget issue.
  2. **Constrain yt-dlp's JS-interpreter / player-client options** so the Deno subprocess is not spawned (or a lighter interpreter is used). That is an extractor argv/options change, deliberately **out of scope for this measurement fix**; it needs its own task plus a re-measurement.
  3. **Re-baseline the §9 budget** if the transient interpreter is judged unavoidable, since the current rows assume only a Python transient. That is a spec/controller decision; this report cannot grant it.
- **Pipeline: WORKS end-to-end.** YouTube "Me at the zoo" (jNQXAC9IVRw) completed the full pipeline — yt-dlp extraction + 8-connection segmented download + ffmpeg merge — producing 475,961 bytes in 14,553 ms (`out/Me at the zoo.mp4`). The Reddit sample errored honestly at extraction: the native Reddit extractor failed (Reddit blocks its `siphon/0.0` user-agent) and the yt-dlp fallback reported "Account authentication is required" for that post. The router fallback and error reporting behaved as designed; a Reddit access strategy (browser-like UA and/or cookies) is an M1+ concern, not an M0 pipeline break.
- **Throughput caveat (NOT validated):** the measured 0.03 MB/s is for a ~19 s, ~0.45 MB clip and is dominated by yt-dlp process spawn + connection setup, NOT steady-state download speed. It CANNOT validate the spec's "2–5x cobalt on large files" claim. No cobalt baseline was measured and no single-stream comparison was run in this spike. The segmented downloader's speed advantage is architecturally proven (Task 7) but not benchmarked at scale here; a large-file throughput benchmark is deferred.
- **Startup < 300 ms (NOT measured):** `elapsed_ms` is total download time, not cold start. Bench does not measure startup latency; cold-start measurement is deferred to the M1 Tauri app. No startup figure is claimed.

Overall: **NO-GO on the RAM hard gate (400.7 MB > 150 MB).** Pipeline feasibility is proven; the resource budget is not. Adjust per spec line 215 and re-measure before building UI. Throughput and startup remain unvalidated (deferred), so no performance certification is made.
